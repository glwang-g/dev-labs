# 第一轮试教

## 当前完整路线的教师闭环

当前默认使用 JavaScript 订单系统的 13 个能力单元。维护者先完整体验，真实学员试教尚待开展；下方九任务流程保留为旧体验路线参考。

1. 学生完成单元训练并参加独立考核。教师切换到“学习详情”，选择该单元，查看尝试、提示和已结束考核；正在进行的考核仅显示进度。
2. 结合真实操作，在“记录观察与追问”关联单元或某次考核，记录问题、具体表现、结论和实际帮助。未现场观察时选择“尚未观察到”，不补填模拟结果。
3. 如需补练，选择实际覆盖的薄弱概念，写明原因与验证建议，并关联观察/考核。学生工作台收到指定补练待办。
4. 学生完成要求数量的新任务。系统保存失败与成功尝试，同题重试不增加多个通过名额；达到要求后进入“待教师追问”。
5. 教师查看补练前后记录，换一个输入或表达式追问，记录“已展示理解”或继续一轮补练。教师结论不会覆盖自动考核成绩，独立再考仍按原门槛执行。
6. 学生在学习日志回看反馈；教师可查看失败考核、后续补练、复核与独立再考的历史。导出时保留已结束记录，不泄露正在进行的考核内容。

第一条链路先用 S0“变量、表达式与赋值”验收，再复用到全部单元。功能验收使用独立测试记录，不作为真实学员的教学效果证据。


## 范围

先邀请 5–10 名近乎零基础学生，使用同一版本的九个任务。先观察任务是否清楚、环境能否使用、帮助是否有效，不据此作普遍就业效果承诺。任务按能力推进，不承诺固定完成时长。

## 每次训练

完成方式由教学用途决定：基础练习直接通过，关键概念做一道简短检查，独立验证与工程交付再写解释。同一轮累计两次未通过时引导复盘，避免把填写解释变成每题的固定负担。

1. S0 要求先预测，允许错误，不先展示答案。基础题答对即继续，不逐题要求解释；阶段抽查时再让学生说出每一轮的变量变化。
2. S1 先明确输入、输出与业务规则，再实现函数。测试失败后先提出假设，再逐级给提示。
3. 独立变式时观察学生实际操作。查文档可以保留，但完整 AI 答案不能作为独立能力证据；外部帮助需单独记录。
4. S2 先阅读三个模块的职责。让学生解释 store 与 app 的依赖关系、HTTP 状态码，以及测试为何要换数据。
5. 最后查看 Git diff 和提交说明，要求学生运行完整回归，讲清如何复现与验证改动。
6. 在人工复核页记录具体追问及表现，而非“感觉懂了”。一周后在界面进行延迟复测，另由教师出一道未见过的小变式。

## 建议追问

- S0：如果移动这一行赋值，结果为什么会变化？
- S1：空订单、刚好等于门槛、全部取消会怎样？为什么采用这类数据结构？
- S2：如果文件损坏，为什么不能直接返回空数组？保存后新实例是否能读取？请求不存在的路径会得到什么？
- AI：你采纳了哪条建议？如何证明它有效？有没有拒绝过错误建议？

## 观察指标

分别记录首次独立完成耗时、主要错误、累计提示量、独立变式表现、教师追问表现与延迟表现。对比原题通过和变式通过，定位是需求理解、语言应用、调试还是工程操作的问题。不把单个通过率折算成就业能力。

当前版本只有本机数据与导出，没有班级后台、自动提醒或教师身份验证。每位学生使用独立数据目录；交付证据 JSON 可能包含学生代码和解释，分享前由本人确认内容。

## 现场执行清单

每名学员使用单独的 DEVLABS_DATA_DIR，避免混合记录。不要求记录真实姓名，另由教师保存学员编号对应关系。开始前记录是否接触过变量、循环、函数和 Git；在“试教记录”填写基线。学习时让学生自行操作，只记录卡点及帮助，不代替完成。S0/S1 结束分别出一道未见过的变式，记录是否独立完成。S2 要求从练习目录实际启动服务、运行测试、解释 Git 改动。七天后做新的同能力变式并记录延迟表现。最后导出该学员的 JSON 证据。

建议变式：S0 改变订单状态并追踪两次处理后的金额；S1 统计退款金额并排除未支付记录；S2 新增一个按客户筛选的 GET 接口，明确空结果、未知路径与非法方法。教师按需求理解、独立实现、验证方法逐项记录，不只按自动测试评分。

首轮目标为 5–10 名真实学员。当前仅完成试教工具与流程准备；尚未招募或完成真实试教，不填写模拟学员结果。
