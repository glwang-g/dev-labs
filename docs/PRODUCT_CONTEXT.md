## 2. 已确认的目标与原则

### 2.1 覆盖三类人群的统一渐进式训练体系【用户确认】

用户明确选择：“我希望 DevLabs 实现 D：建立覆盖三者的统一渐进式训练体系。”

三类需求为：

| 进入时的状态 | 想获得的能力 | 产品应提供的价值 |
| --- | --- | --- |
| 零基础或近乎零基础 | 理解、编写和修改基础程序 | 从概念理解走向独立操作 |
| 会写基础代码、准备参与真实工程 | 接手项目，完成初级工程师任务 | 阅读、修改、测试和交付工程代码 |
| 已掌握某种语言或技术栈 | 迁移到新的语言、框架或运行时 | 复用旧知识，识别差异，验证新实现 |

用户此前澄清最初想做的是“教学生开发”的方向；之后选择覆盖三者。因此不能把早期助手提出的“求职能力评测平台”或“以能力证明为主”当作最终定位。能力反馈服务训练，不等于招聘认证。

### 2.2 自由进入、独立获益、退出与恢复【用户确认】

用户明确要求：“一个人可以从任何阶段切入，并且在其中得到自己想要的，而且可以随时离开，也可以随时回来。”

该原则约束体验：零基础可学基础；已有能力者可进入工程或迁移任务；只解决一个具体问题的人也应得到完整价值。成长体系不能要求所有人完成同一条长课程，离开也不应意味着学习成果丢失。

## 3. 产品定位与竞争讨论

### 3.1 算法平台之间的差异

以下是高层用途比较，不是平台功能穷举，也不代表用户已选定竞争策略。

| 平台 | 主要使用场景 | 对 DevLabs 的启示 | 来源状态 |
| --- | --- | --- | --- |
| 洛谷 | 中文算法学习、题库训练与信息学竞赛 | 用户已有明确竞赛目标时，DevLabs 不必争夺其刷题入口 | 原对话讨论 |
| AtCoder | 算法竞赛及围绕比赛题目的训练 | 竞赛解题能力与真实工程交付能力应分别描述 | 原对话提及竞赛用途；此处展开为本次补充 |
| Codeforces | 算法竞赛、竞赛评级及题目训练 | 竞赛反馈清晰；DevLabs 需找到自己的任务和反馈闭环 | 本次补充，未检索到原对话详细讨论 |
| LeetCode | 算法练习与技术面试准备 | 不是所有开发能力都能用单函数题和算法效率评价 | 原对话讨论 |

【助手建议】DevLabs 可聚焦“在工程约束下理解、实现、调试、测试和交付”，与算法平台形成互补。不能因此断言算法平台没有其他内容，或学生一定需要 DevLabs。

### 3.2 更直接的替代方案：视频教程、GitHub 与 AI【助手分析】

用户已经可以通过视频学习语言和框架，在 GitHub 阅读真实项目，向 AI 请求解释、计划、练习和代码。三者组合已能支持一条学习路径，DevLabs 必须证明额外价值。

| 替代方案 | 已能提供的价值 | DevLabs 拟验证的增量 |
| --- | --- | --- |
| 视频教程／教材 | 系统讲解、示范与跟练 | 从“看懂和跟写”到独立解决新任务的训练 |
| GitHub | 真实源码、项目与协作材料 | 适合当前能力的任务、明确边界和可检查结果 |
| AI 编程与对话工具 | 随时解释、生成代码、调试和个性化辅导 | 可操作实验、过程证据、独立变式和学习状态恢复 |

【助手建议】定位为经过设计的软件开发训练环境：理解机制 → 亲手操作 → 在真实项目中应用 → 验证能力。仅组合“课程 + 在线 IDE + AI 助教”未必形成优势。

【待验证假设】这种环境比上述替代方案更能缩短理解到应用的距离。需求真实、愿意尝试、愿意持续使用和愿意付费是不同问题，均不能从教育价值推导出来。

早期“入职挑战、工程能力报告、帮助求职”的提案保留为候选场景，不能替换用户后续明确的统一训练目标，也不承诺就业效果。

## 4. CodeMuseum、xshow、DevLabs 的职责

【原对话助手建议】三者形成统一体系，而非三个割裂的教育产品：

| 组成 | 原讨论中的职责建议 |
| --- | --- |
| CodeMuseum | 计算机概念与运行机制的可视化理解：为什么这样运行 |
| xshow | 编写、运行、观察与调试：亲手实现并验证 |
| DevLabs | 任务组织、训练路径、工程实践与能力反馈 |

【现有文档事实】当前 README 的职责表述为“CodeMuseum 负责语言探索；xshow 负责机制实验；DevLabs 负责任务训练与能力证据”，与早期建议的具体边界不完全相同。当前 DevLabs 独立实现核心逻辑，仅链接外部资源，未接入两者私有执行服务。

【待决】长期分工应结合三个项目真实接口再统一命名。共同方向是理解工具、操作实验和训练组织互补；不根据早期建议擅自调换项目职责，不把集成两者作为 MVP 启动前提。

## 5. 统一能力网络与渐进训练

【助手建议，响应用户自由进出原则】用能力与依赖关系组织内容，而非强制线性课程，可概括为“学习有体系，使用无路径”。这句表达及以下机制由助手提出，不是用户逐项确认的实现方案。

- 能力节点支持独立进入；连线表示依赖、关联或可迁移知识，不默认表示强制解锁。
- 提供推荐路线，遇到缺口按需补足，而非一律回到第一章。
- 同一能力跨层次复用。例如函数从参数、返回值和作用域，延伸到模块接口，再到不同语言类型与调用机制的比较。
- 每次学习都有明确目标、可验证结果和可带走的收获；短时体验也应独立成立。
- 可保存代码、实验状态、问题、已获得证据和下一步建议；返回时恢复上下文，比只保存完成百分比更有用。
- 不依赖强制签到、连续学习压力或强制解锁维持留存，是助手提出的体验建议。

原讨论曾建议 L1 编程基础、L2 软件工程、L3 技术栈迁移。这是能力分类，不是要求所有人从 L1 顺序读完。它也不等同于当前实现的 S0 程序认知、S1 语言应用、S2 工程基础；当前三个 S 阶段尚未覆盖长期全部目标。

【当前差距】现有默认路线仍要求单元训练、独立考核和阶段综合考核，并在通过后解锁下一阶段。这是当前切片的实现规则，尚未兑现任意阶段进入的长期原则。需要后续明确区分“进入学习”与“取得能力证据”的条件；本文不修改既有门槛，也不宣称冲突已解决。

## 6. Lab 最小学习单元【助手建议】

| 组成 | 最小内容 |
| --- | --- |
| 目标 | 本次解决什么问题，完成后获得什么 |
| 前置知识 | 建议基础与按需补充入口，不默认强制修完 |
| 实验环境 | 能立即运行、观察或操作的材料与环境 |
| 任务 | 亲手完成的一件具体事情，明确输入和约束 |
| 验证 | 检查结果与理解；需要时使用独立变式和工程证据 |
| 关联 | 相关概念、补足基础和继续深入的节点 |
| 快照 | 保存代码、操作状态、问题与恢复位置 |

Lab 应相对独立，同时连接更大的能力网络。不是每个 Lab 都要有大型工程、长篇解释或 AI；验证形式按教学目标决定。原对话的短时实验例子不构成统一时长承诺。

## 7. AI 贯穿各阶段【助手建议】

AI 是跨阶段工具，不是孤立的第四阶段。

| 阶段 | AI 的角色 | 学习者仍须展示的能力 |
| --- | --- | --- |
| 基础编程 | 提示、解释、辅助调试 | 理解并编写基础代码，预测和解释变化 |
| 工程实践 | 辅助开发、生成测试、代码审查 | 理解、验证和维护工程改动 |
| 技术栈迁移 | 探索陌生生态、比较方案、协助迁移 | 识别差异、判断输出、验证行为 |

【现有项目约定】帮助和模型请求由学生显式触发；建议不自动执行或覆盖代码；独立变式和延迟复测关闭平台内帮助。不能据此保证没有使用外部 AI，也不能把 AI 生成、测试通过、解释字数或模型评分当作掌握证明。

【待验证假设】帮助逐渐减量、配合独立任务与追问，能提高真实能力而非仅提高原题通过率。

## 8. 首版 MVP：原建议与当前切片

### 8.1 原讨论中的候选方案【助手建议，未定案】

早期建议用仓库、任务说明、自动测试和简单评估页验证工程挑战；用户选择统一体系后，助手举例以 Python 串联基础、算法、模块调试、API/SQLite、陌生工程任务和小规模技术迁移。之后用户强调自由进出，建议进一步收敛为先验证标准 Lab 的独立价值、知识关联和恢复。

这些是讨论演进中的方案，不能把 Python、SQLite、Rust 迁移或整条六步路线视为用户指定的首版范围。长期覆盖三类需求，也不意味着第一版同时建设三个完整阶段。

### 8.2 当前已有 MVP【现有文档事实】

当前是无第三方运行依赖的 Node.js 本机单学员 MVP，默认采用 JavaScript 订单系统的 S0–S2、13 个能力单元；保留旧九关与条件分支样板作为参考。包括训练、独立考核、补练、教师观察、历史证据和本机恢复；S2 使用真实多文件工程、文件持久化、HTTP 与 Git 交付。

当前不代表完整初级工程师能力、技术栈迁移训练或就业认证。第三方依赖安装、数据库、生产部署、多人协作及陌生企业仓库仍在范围之外；跨设备草稿恢复也未承诺。平台仅适用于本机可信学员，不能直接当作公网多租户运行环境。

建议下一轮优先以已有切片验证 Lab 是否成立，避免为统一能力网络先建完整平台。具体试教执行遵循 [PILOT.md](PILOT.md)，范围以 [ROUTE_COVERAGE.md](ROUTE_COVERAGE.md) 为准；旧样板说明与当前完整路线不可混为一谈。

## 9. 验证假设与证据计划

原讨论提出独立完成率、工程迁移能力和学习持续性；持续性只能作为自愿获得后续价值的信号，不能违背随时离开原则。本次整理将原分析转为以下验证项，均非已验证结论或用户批准的量化指标：

| 待验证假设 | 可收集的证据 |
| --- | --- |
| 用户会为具体开发问题选择 DevLabs | 实际进入动机、任务选择、与视频/GitHub/AI 的使用比较 |
| 单个 Lab 即可独立获益 | 无需完成全路线也能解决目标问题；任务前后的新变式表现 |
| 训练能迁移到未见任务 | 未见输入、不同结构任务、陌生项目修改及验证解释 |
| 可视化和实验促进理解 | 预测与操作记录、错误假设修正、与普通解释方式的比较 |
| AI 帮助后仍能独立完成 | 实际帮助量、独立变式、教师追问和延迟表现 |
| 退出后能够有效恢复 | 中断后恢复代码、状态和问题所需操作，是否能继续完成目标 |
| 跨技术栈能复用已有能力 | 在另一技术栈完成等价任务并解释差异；当前 MVP 尚未提供此证据 |

现有试教计划为 5–10 名真实学员，记录基线、卡点、帮助、变式和七天后表现；维护者完整体验先于真实学员试教。项目文档显示工具已准备，真实试教尚待开展。本次未新增试教结果。自动测试、模型模拟、维护者体验均不能替代真实教学效果。

## 10. 未决问题

1. 第一批优先服务哪类用户、哪种具体任务？长期统一目标不自动决定首批招募范围。
2. 内容主线以概念实验还是逐步复杂的真实项目组织？如何兼容两者与独立进入？原对话提出但未回答。
3. 如何用可选诊断推荐入口，同时保留直接进入？哪些考核门槛只约束能力声明，而不阻止学习？
4. 标准 Lab 的状态快照保存哪些字段？如何支持版本变化、环境重建与更长期恢复？
5. 三个项目最终职责、接口和链接粒度如何统一？是否需要共享能力标识，而非共享整个应用？
6. 独立能力证据如何处理外部 AI、同题记忆与模板熟悉度？不同教学目标各需什么验证？
7. 当前严格通过门槛与提示减量策略，是否适合真实零基础学习者？应由试教校准。
8. 技术栈迁移最先验证哪一组语言或框架？如何区分知识迁移与重新跟写？
9. 谁维护持续变化的工程内容，如何控制制作与维护成本？
10. 用户是否愿意持续使用或付费，工程能力反馈是否有外部认可？商业模式、认证与就业承诺均未定案。

## 11. 后续协作边界

## 12. 2026-11-13 本会话增量决策与实现

用户确认“每个关卡可以设计为最小 Lab”，并提出直接进入单元时可有预设考核；随后授权按可跳过入口诊断、自由探索与出口验证分离的思路改版。

当前版本将既有 45 个训练位组织为稳定 ID 的 Lab，开放单元/关卡进入，保存各自普通任务与草稿，并增加可跳过的两题入口诊断、桥接返回以及独立考核暂停恢复。既有能力验收条件继续用于通过记录，不再作为阻止进入学习的条件。推荐路线仍保留。

这是上述“当前差距”的局部落地，不代表完整能力网络、跨栈诊断或独立工程环境已经完成。当前只有 JavaScript 订单系统；S2 共享真实练习工程。诊断内容、90 天参考期及教学效果仍需试教校准，详见最新 README 与 ROUTE_COVERAGE.md。
